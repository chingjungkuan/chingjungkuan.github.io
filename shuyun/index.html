概述 Overview

舒運 — 客運訂票 App

#B2C #Side Project #iOS App

Team | Side Project（個人作品）

Role | UI/UX Designer

工具 | Figma・Xcode（SwiftUI Prototype）

  • 產品服務｜一款針對客運訂票流程設計的 iOS App，讓使用者能快速搜尋班次、選位、填寫乘客資訊、完成付款，並管理所有票券。
  • 專案挑戰｜台灣現有客運 App 操作複雜、資訊層級不清，關鍵動作（選位、確認班次）藏在多層頁面中，導致使用者在訂票過程中頻繁迷失或放棄。
  • 設計策略｜以「資訊層級清楚傳達給用戶」及「明確引導使用者完成每一步」為核心原則，將訂票流程重新拆解為線性步驟，降低認知負擔。
  • 洞察轉化｜透過一對一訪談挖掘使用者真正的操作斷點，將痛點轉化為具體的設計決策，而非只是視覺美化。

Emphasize Research

研究方法：訪談法

採取一對一訪談的方式，深入收集相關人士的意見、經歷與使用場景，了解不同用戶群體在意的部分和潛在需求。

▍研究目標

  • 人們對於交通票的購票方式為何？
  • 人們如何查詢搭乘的相關資訊？
  • 他們在意的資訊有哪些？對於購票有什麼要求？
  • 人們的期待或是願望？

▍訪談摘要

  • 對交通類型 app 的功能需求：訂票、查詢時刻表、搭乘資訊、車種差異、失物招領、誤點提醒、一段票與兩段票提示。
  • 期待體驗：效率高，操作容易。
  • 多數使用者偏好線上付款，因為方便快速。
  • 多數受訪者不知道有客運 app；即使有，下載後因操作困難而退卻。

Persona Define

三個核心用戶畫像

▍羅紹閬（21y）大學生

行為與需求

  • 希望可以提前去查詢客運詳細的搭乘資訊，快速比較不同車種與票價的差異。
  • 因為要打工的緣故，時間不固定，希望可以彈性規劃自己購票的時間，不用多跑一趟。
  • 常常會和妹妹一起搭車返鄉，有時和朋友旅遊也會一起訂票，會希望分票的方式是容易且好上手的，並且希望位置可以坐一起。

動機

  • 有搭車需求時，可以快速查詢時刻表，去衡量要搭車的選擇和時間。
  • 可以提早app買票和劃位。
  • 當初會下載app是因為朋友要分電子票給我，讓我可以用手機的條碼進站搭車。
▍李嘉敏（29y）上班族

行為與需求

  • 返鄉訂票的流程希望可以大幅減少花費的時間，希望訂票的介面簡約俐落容易操作上手。
  • 因為要上班的緣故，不希望還要花時間到實體的店面或是臨櫃去做買票的或是查詢的動作。
  • 希望可用自己有空的時間，最快速方便的方式去劃位。

動機

  • 查詢時刻表，去衡量要搭車的選擇和時間。
  • 有要搭車的需求時，直接透過app買票和劃位。
▍陳宗翰（38y）自由接案者

行為與需求

  • 需要知道車子的即時狀況和最新消息，才知道要如何搭車。
  • 有固定的需求，如果有會員制可以更方便紀錄一些
  • 因為搭車的行程較為固定，因此會希望可以加快整個訂票的過程，不用每次都要重新輸入一次。
  • 因為時常會自己出遊，可以讓家人知道自己的位置比較心安。

動機

  • 有要搭車的需求時，需要透過app買票和劃位，選擇自己想坐的位置。
  • 臨時想旅遊時，會想了解目的地附近的景點。

痛點與任務 Pain Point & Task

現有客運 App 的操作困境

找不到想要的班次

現有 App 的搜尋結果缺乏有效排序與篩選，使用者必須逐筆掃描才能找到合適班次，增加決策成本。

選位畫面看不懂

座位狀態未明確視覺化，可選與已售出座位的區別不清楚，使用者容易誤觸或放棄選位。

不確定有沒有付款成功

付款完成後缺乏清楚的確認頁面，使用者需再進入訂單頁查找，降低對 App 的信任感。

資訊層級混亂

時刻、價格、剩餘座位以相同視覺權重並列，使用者無法快速抓到關鍵資訊，認知負擔高。

流程缺乏引導感

從搜尋到付款沒有步驟提示，使用者不清楚自己目前在哪個環節，容易中途放棄。

多數人不知道有客運 App

即使知道並下載，操作困難讓使用者直接退出，改用傳統電話或現場購票。

設計決策 Solution

針對訪談揭露的三大斷點，設計重心放在「讓使用者在每一步都知道自己在做什麼、下一步要去哪裡」。

強化資訊層級

班次列表將時間與價格放大顯示，剩餘座位以警示色提示，使用者不需逐行掃描就能快速判斷。

線性步驟引導

搜尋→選位→填資料→付款→確認，每個步驟獨立成頁並附帶進度指示，清楚告知目前位置。

選位視覺化

以色塊區分可選・已選・已售出・商務艙四種狀態，操作即時回饋，不產生歧義。

付款完成即展示票券

確認頁直接呈現路線、座位、登車月台與 QR Code，不需再進入訂單頁查找。

目標用戶

18–35 歲、定期搭乘客運的通勤族與旅遊族。重視效率與操作簡便，多以手機完成訂票。

設計核心原則

資訊層級清楚傳達給用戶、明確引導使用者完成每一步。所有設計決策回扣訪談洞察，不做假設。

資訊架構 Define

先梳理 App 所有功能模組，依據訂票核心流程與輔助功能拆分層級，建立清楚的 IA 供後續 UI 設計依循。

Story Board Ideate

以真實情境描繪使用者從發現需求到完成訂票的完整旅程，確保每個設計決策都有情境依據，而非憑空假設。

Wireframe Ideate

依據 IA 與 Story Board 產出低保真線框稿，確認頁面結構與操作流程後，進入視覺設計階段。

UI Design

清晰的色彩系統，讓每個操作狀態一目了然

以「舒適」與「可信任」為視覺基調，選用綠色（#2DB87A）作為品牌主色，傳遞自然、安心的出行體驗；橘色（#F5942A）作為強調色，標示促銷與警示資訊。

▍註冊

以簡單 3 步驟完成註冊：填 Email → 驗證信箱 → 輸入會員資料。每步只要求填寫最少必要資訊，避免讓新用戶在起點就感到負擔。

驗證信箱步驟中，透過文字再次提醒使用者填入的 Email，方便確認是否有誤，降低重新填寫的挫折感。

▍訂票

訂票頁面讓使用者專注於「訂票相關的」內容選擇，直觀訂購體驗，同時確保不錯過重要的最新消息。

在最上方放上最新消息的跑馬燈，讓使用者在訂票的同時不會錯過最新資訊。流程分為：輸入搭乘資訊 → 選擇班次版次 → 選上位置 → 最終訂票資訊填寫 → 線上付款。

▍待處理

用 Tab 的方式讓頁面區分 3 種不同的狀態：未付款・未取票・待分票，讓使用者可以知道目前不同狀態的票有哪些，依照自己的需求去選擇要處理的票券。

票券呈現採用卡片的方式，獨立出每張票券讓使用者可以更明確的區別，快速選取想要選擇的票。

▍查詢

共有 3 種查詢的方式，分別是「時刻・路線資訊・營業據點」，此三個頁面皆是以查詢和獲取資訊為主要目的，因此將畫面的重點放在查詢的搜尋框和資訊列表。

▍更多・會員

「更多」頁面彙整常用功能入口，「會員」頁面整合個人資料、付款設定、通知偏好等帳戶管理功能，讓使用者不需在多個頁面間來回切換。

整個訂票流程以 SwiftUI 實作成可互動 Prototype，在 iPhone 模擬器上即可完整體驗從搜尋到取得票券的完整流程。

Takeaway

這個 Side Project 讓我有機會從零開始主導一個完整的產品設計流程，從訪談、定義問題到 UI 實作，每個決策都需要自己提出理由並驗證。

流程設計比視覺設計更難

訂票流程的每一步都是使用者決策點，如何減少每個步驟的認知負擔、讓使用者始終知道下一步要做什麼，遠比讓畫面看起來好看更難。這次讓我更深刻理解「設計是解決問題」這件事。

訪談是最直接的設計輸入

我本來以為選位畫面最難設計，結果訪談後發現使用者最在意的是「付款後有沒有成功」。這提醒我，設計決策不應該從自己的假設出發，而是要回到使用者真正的使用情境中找答案。

把設計做到可以跑起來

用 SwiftUI 把整個 App 實作成可互動的 Prototype，而不是只停留在 Figma Mockup，讓我第一次感受到設計在真實裝置上的重量、間距、動態反饋有多重要，也更理解工程師面對 Spec 時的思考方式。
